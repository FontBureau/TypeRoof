#Research: Named justification-potentials configurations

#Research Question

Enable selecting a justification-potentials variant beyond auto-discovery, for BOTH greedy-fit and knuth-plass: a potentials choice of “auto” (current best-fit discovery) or a named configuration — first entries: the headline wdth-narrowing treatment from the varla-varfo WDTH_JUSTIFICATION_SPECS stub, folded into the unified potentials structure with a real dflt slot. Named selection must be “maximally graceful”: no family/axis gating, missing navigation dimensions filled from table-declared defaults or manual overrides, treated axes the font doesn’t support applied anyway (no-ops). Generalize the treatment config: any number of axis tags plus optional tracking/wordspace, replacing the hard-coded trio.

#Operator briefing (decisions of this session — the feature contract)

  • The wdth stub semantics: h1/“main” headlines sit at the WIDE end (RobotoFlex wdth 151, AmstelVar 125) and ONLY narrow; the dflt slot IS the wide end, so widening potential is zero by construction: { wdth: [35, 151, 151] } (RobotoFlex) / { wdth: [50, 125, 125] } (Amstelvar); provenance comments carried over, incl. the “widening not confirmed” FIXME.
  • PotentialsTable gains defaultLocations: number[] parallel to dimensions — the modeling font’s defaults, used when the run’s font lacks a dimension’s axis. The existing RF/Amstelvar full tables get theirs declared (verify against the shipped fvar).
  • Named configurations = a flat map selected BY NAME. NO family matching, NO axis-existence gate. Graceful piecewise: missing nav dims -> defaultLocations or manual override; treated axes the font lacks -> applied anyway (render/measurement no-ops; the line justifies via the remaining treatments); no effective overlap -> step 0 everywhere, “we just render the font”, never an error.
  • Config names: enum (auto, robotoFlexText, robotoFlexHeadline, amstelvarText, amstelvarHeadline). auto = today’s best-fit discovery, explicitly restricted to the Text pair (behavior identical to the current registry, which is exactly those two tables). *Text = the existing full tables (their wdth-100 branch is commented “default reading text spec”); *Headline = the flat wdth tables. Future: more advanced selection (family + useCase like “text”/“headline” per font) is explicitly OUT of scope now.
  • potentialsLocationOverrides: ordered map axis tag -> NUMBER (no logical values); FILL-ONLY — applies only to dimensions the run’s font does not carry; entries for axes the font has are ignored. Precedence: override > defaultLocations. Fill-only protects the step-0-identity invariant (overriding an axis the run uses would re-anchor the treatment away from the run’s actual value and change rendering AT step 0).
  • The documenting string (“the potential is selected by: opsz(14), wght(400), wdth(100)”) is GENERATED from the effective location, not stored (cannot drift out of sync).
  • Treatment config generalization (“not hard-coded to 3 treatments”): axisTreatments: "all" | ReadonlySet<string> + tracking / wordspace booleans. Greedy-fit struct: treatmentAxes = list of validated axis tags (empty = all axis treatments of the resolved table), treatmentTracking/treatmentWordspace booleans stay (they already exist); treatmentXTRA is DROPPED, no migration. KP keeps planner defaults (all treatments on, direction “both”), gaining only potentials + potentialsLocationOverrides.
  • No changes to the pure algorithms (greedy-fit.ts, knuth-plass.ts); the anchoring/measurement/applicator paths are already graceful (evidence below).
  • CORRECTION (operator, 2026-10-14 19:42): the potential’s authored span IS its identity — the headline config MEANS “start at 151, narrow toward 35”. It is not a font-derived range: recasting the config on another font as a “[75,100] narrowing potential” misrepresents the authored semantics.
  • Anchoring becomes a TRIPLE-valued OPTION (operator 2026-10-14 20:04; presumably a struct knob next to potentials, default “run”, to confirm in planning) — potentialsAnchoring: "run" | "font" | "off":
    • “run” (default, STATUS QUO): today’s anchorPotentialsToLocation, unchanged (dflt := the run’s RESOLVED axis value — the style’s explicit setting or the font’s axis default when unset, never the table’s authored dflt; min/max shifted by the same delta, clamped to font.axisRanges — step 0 is “no change” by construction). The auto path and existing tables are untouched.
    • “font”: dflt := the FONT’s axis defaults (fvar), regardless of where the style pushes the run — one stable anchor per font, shared by all runs; min/max shifted + clamped as above. Step 0 = the font’s default position: no change only for runs not styled away from the defaults. (Operator 20:07: this run-independence is exactly the point — stable, consistent potentials across runs of the same font, unaffected by where styles push individual runs.)
    • “off”: no anchoring — authored triple verbatim. Regardless of the run’s current value / the font’s axis default, the treatment starts at the CONFIGURATION’s own dflt (the mid slot of the triple, e.g. 151) and traverses the authored span; values the font cannot reach clamp at the application boundary (HarfBuzz and CSS both clamp to fvar — measurement/render parity holds), i.e. the existing no-op machinery for unsupported axes. NOTE: with “off”, step 0 applies the authored dflt — for a run not sitting there, step 0 is no longer the run’s unadjusted state (the configuration asserts its natural state; a conscious authoring statement, differs from the step-0-identity invariant elsewhere).

#Summary

The pipeline is ready for this feature: the Treatment Planner is already generic over arbitrary axis tags (only struct fields, properties-generator lists and the controller’s toggle mapping hardcode the trio); measurement and rendering already no-op treated axes the font lacks; anchoring already clamps to the font’s axis ranges (a wdth table cross-applied to another font yields sane, cross-applied to another font degrades gracefully). The work is: data (wdth tables + defaultLocations), a named-configuration map + graceful resolver in justification-potentials.ts, config-shape change in treatment-planner.ts, struct fields + properties-generator entries

  • widget mappings on the metamodel/UI side, controller wiring for both algorithms, and the generated selection doc string.

#Detailed findings

#Potentials data model & resolution

  • lib/js/components/layouts/type-stage/text-composition/justification-potentials.ts
    • PotentialsTable :42 (dimensions + tree; to gain defaultLocations), PotentialsLevel/leaf types :26-40. Leaf = treatment triples [min, dflt, max]; axis treatments are 4-char tags, tracking is ABSOLUTE pt, wordspace a FACTOR of the natural space advance.
    • validatePotentialsTable :66 — leaf key-set uniformity across ALL leaves, triple min<=dflt<=max, numeric monotonic levels; both stub tables validated at module load.
    • calculatePotentials :164 — separable multilinear interpolation, levels bottom out early, out-of-range clamps to edge stops; THROWS when the location misses a dimension (the guarantee that named selection must relax); step-0-identity dev warning for axis treatments.
    • anchorPotentialsToLocation :247 — re-anchors axis triples to the run’s location (dflt := run value, min/max shifted, clamped to font.axisRanges); a treated axis ABSENT from the location keeps the authored triple unclamped (graceful for unsupported axes). UNCHANGED when the anchoring option is ON (status quo); OFF skips it entirely (authored triple verbatim).
    • _POTENTIALS_REGISTRY :549, discoverPotentials :586 — best-fit: longest family-name prefix, then most required axes; requires ALL navigated/treated axes present in font.axisRanges (the gate that named selection must NOT apply).
    • Data: JUSTIFICATION_POTENTIALS_AMSTELVAR / _ROBOTO_FLEX (verbatim varla-varfo port; the wdth-100 branch is commented “default reading text spec” — the natural *Text configs).

#Graceful application paths (evidence “apply anyway” is safe)

  • Measurement: .../measurer.ts axesEntriesOf :33-52 — location is built from font.axisRanges only (an axis the font lacks is absent from the location); axesAtStep drops unknown tags; HarfBuzz shapes at the font’s real axes. Measured == rendered for no-op axes.
  • Rendering: .../line-attrs.ts lineSpanStyles :199-224 — per-line-span font-variation-settings (unsupported axes ignored by the font), wordspace = factor * natural space advance, tracking via shaped glyph counts; viewer.typeroof.jsx applies it per fragment.
  • Anchoring (mode examples, the triple from 20:04): the Flex headline table {wdth:[35,151,151]}: a run AT wdth 151 (the h1 case) is the identity case — narrowing-only by construction. A plain-Roboto run at wdth 100 with “run” (status quo) re-anchors per today’s code to [75,100,100] (dflt := 100, shifted + clamped). With “font” the anchor is the font’s fvar default (plain Roboto wdth 100 → same [75,100,100]; a run STYLED to 90 would still anchor at 100, step 0 moving it back). With “off” the authored triple applies verbatim: the treatment starts at 151 and the font clamps applied values at its boundary (plain Roboto renders the start at its max 100 and narrows along the authored span until its floor 75). A font without wdth keeps the authored triple, applies it, ignores it.
