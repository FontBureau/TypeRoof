# Research: Videoproof keyMoments ownership (generated vs. user data)

## Research Question

Prepare the discussed refactor: in the **videoproof layout only**, animation-driving
keyMoments of VideoproofArrayV2 actors are always generated by axesMath (never
user-edited, never serialized), while property-setting keyMoments (root layer actor,
cell keyMoments[0]) hold user data and serialize. The same actor models are shared
with motion-stage, where keyMoments ARE user-editable — the tighter regime must not
leak out of the videoproof layout.

## Summary

- The current implementation marks generated keyMoments with a `GENERATED_DATA`
  symbol; the marker lives on the state instance and is lost whenever a user edit
  creates a new immutable (drafts never copy own symbol properties). This makes the
  generated/user-owned distinction implicit and fragile.
- All user-facing edit widgets in the videoproof layout bind to fields of
  `keyMoments/0` of the VideoproofArrayV2 actor (charGroup, cellAlignment,
  textColor, stageBackgroundColor, languageTag, openTypeFeatures, showCellBoxes);
  there is NO keyMoments list editing UI in videoproof. The only list consumers
  (renderer, UIAxesMath) are read-only.
- The property inheritance machinery (HierarchicalScopeAnimanion) fully supports
  root-layer → V2 actor → cell inheritance for charGroup/showCellBoxes/cellAlignment,
  but the root layer's keyMoment model (TypeSettingKeyMomentModel) currently lacks
  those fields, and stageBackgroundColor is deliberately inherit:false.
- Motion-stage edits the same keyMoments models through fully generic machinery and
  never sets GENERATED_DATA; cross-layout copy/paste is NOT implemented (intra-layout
  drag only).
- There is no state-file versioning/migration mechanism; coherence functions are the
  de-facto load-time "migration" pattern already in use (initCellKeyMoments).

## Detailed Findings

### 1. GENERATED_DATA marker lifecycle (metamodel)

- Symbol: `base-model.ts:18` `GENERATED_DATA = Symbol.for("GENERATED_DATA")`;
  default `SERIALIZE_OPTIONS.skipDataMarkers` contains it (`base-model.ts:75`).
- Set on drafts: `axes-math.mjs:495,503` (`keyMoments[GENERATED_DATA] = 'axesMath'`,
  both the V2 actor's and each cell's keyMoments) and `videoproof.typeroof.jsx:1276`
  (initCellKeyMoments, committed fix ca1ed19d).
- Draft → immutable: the draft object itself is frozen
  (`list-model.ts:267-310` `#_lockAndFreeze` / `Object.freeze(this)`), own symbol
  properties survive. Untouched children are reused by identity
  (`list-model.ts:239-247`, `struct-model.ts:647-657`).
- Lost on user edit: `getDraft()` (`base-model.ts:359-370`) constructs a NEW object;
  constructors never copy own symbol properties (no `getOwnPropertySymbols` anywhere
  in lib/js/metamodel/) → marker gone → list serializes fully from then on.
- Serialization consults the marker in `_skipSerialize` (`base-model.ts:542-566`,
  own-property check on the child item), called from `_serializeContainer`
  (`base-model.ts:657-660`); marked children serialize as `null` and are dropped.
- Consequence: marker must sit on the keyMoments LIST (direct child of the actor
  struct) — which is where it is today.

### 3. Property inheritance mechanism and gaps

- Registry: charGroup `registered-properties.mjs:251` (inherit:true), showCellBoxes
  :263 (inherit:true), cellAlignment :277 (inherit:true), stageBackgroundColor
  :106-111 (**inherit:false**, deliberate).
- Chain: each actor gets AnimationLiveProperties (`animation-animanion.mjs:883`)
  wired by `actors-meta.mjs:29-50`; children receive
  `animationProperties@<parent>` as `@parentProperties` (`actors-meta.mjs:46,65`).
  `HierarchicalScopeAnimanion` (`animation-animanion.mjs:1004-1009`) resolves
  leaf → root in `getPropertiesFromGlobalT` (:795-819), passing parent properties
  only when `inherit:true` (`isInheritingPropertyFn`,
  `registered-properties.mjs:382-388`).
- Local values: `initAnimanion` (`motion-stage.mjs:484-492`) with
  `genericPropertiesBroomWagonGen` (:455-466) flattening whitelisted fields
  (`REGISTERED_GENERIC_KEYMOMENT_FIELDS`, :416-419 = charGroup, charGroups,
  showCellBoxes, cellAlignment); empty OrEmpty slots are skipped
  (`registered-properties-definitions.mjs:179-193`), leaving room for inheritance.
- Cells have no own animanion; they read the V2 actor's animationProperties@
  (`videoproof-array.mjs:727-736`), chained to the root layer.
- Consumers: V2 renderer reads generic/charGroup via `_getCellContents`
  (`videoproof-array.mjs:811`, map at :767); cell renderer generic/showCellBoxes
  (:454); controller generic/cellAlignment (:1389) and colors/stageBackgroundColor
  (:1395).

GAPS for moving property-setting to the root layer:
1. `TypeSettingKeyMomentModel` (root layer keyMoments, `models.mjs:151-157,172-196`)
   has NONE of charGroup/showCellBoxes/cellAlignment/stageBackgroundColor → fields
   must be added (mixin) for root-level setting to work.
2. stageBackgroundColor is inherit:false by design → root-level stage background
   requires a deliberate flag change.
3. `getPropertyValuesMapForKeyMoment` (`animation-animanion.mjs:856-858,1064-1067`)
   uses ONLY the local animanion → keyMoment-editing UIs don't display inherited
   values (only the live globalT render path inherits). UX consideration if
   properties move up.

### 4. Motion-stage usage of shared models (must remain unaffected)

- Actor types registered once, shared: `available-actors.mjs:46-59` (incl. V2 actor
  and cell); motion-stage injects all as availableActorTypes
  (`motion-stage.mjs:250-256`).
- Generic keyMoments editing for EVERY actor type: KeyMomentsControls
  (`motion-stage.mjs:1139`; insert :1184-1256, add :1273-1301, remove :1303-1314),
  type-driven KeyMomentController (:1697). Reorder NOT implemented (:1733-1735).
- Stage root has own keyMoments (`StageKeyMomentsModel`, :214).
- Insert-moment does NOT capture generic fields like charGroup (:1253-1258 warns
  NOT IMPLEMENTED).
- Motion-stage NEVER calls applyAxesMathLocations and NEVER sets GENERATED_DATA.
- V2 actor reuses V1 `VideoproofArrayKeyMomentModel` for its keyMoments
  (`videoproof-array.mjs:399`, model at :97-104).
- stageBackgroundColor is not referenced in motion-stage.mjs at all (flows
  generically via colorsGen).
- Cross-layout copy/paste: NOT implemented. Drag/drop is intra-layout, path-based
  (`data-transfer-types.mjs:16-22`; StageManager :669-969; videoproof duplicate
  L574-580 "FIXME: straight copy"). Marker-stripping TODO committed at
  `videoproof.typeroof.jsx:1120-1122` and `axes-math.mjs:488-495` (commit 45d62326).

### 5. State load path and migration options

- Load: `app-menu.typeroof.jsx:135-156` → `deserializeStateString`
  (`state-file.mjs:6-13`) → `deserializeGen` (`serialization.ts:18-41`,
  JSON.parse at :30) → `createPrimalStateGen`; unknown keys silently skipped
  (`struct-model.ts:674-723`, comment mentions "version miss-match" at :703-708).
- Shell: `_updateState` (shell.mjs:1529) → `_asyncMetamorphoseState` (:1461) →
  `__asyncMetamorphoseState` (:1393, fonts resolved) → second pass
  `_syncMetamorphoseState(newState.getDraft())` (:1489) — coherence functions run
  during construction AND again in this pass.
- Replace: `_replaceState` (:1574) → `StateComparison` → `this._ui.update` (:1599).
- NO versioning/migration mechanism exists (layout info only in the file NAME,
  `state-file.mjs:16-24`). Candidate hooks:
  1. app-menu `_onSelectStateFile` (layout-specific, file-menu path only)
  2. `deserializeStateString` (single choke point for strings)
  3. `deserializeGen` after JSON.parse (generic for all deserialization)
  4. coherence functions (idiomatic; already used by initCellKeyMoments)

## Open Questions

1. Where should property-setting fields live for videoproof: add charGroup/
   showCellBoxes/cellAlignment/stageBackgroundColor to TypeSettingKeyMomentModel
   (root layer), or keep UI on the V2 actor's keyMoments[0] with a different
   ownership mechanism?
2. stageBackgroundColor inherit:false is deliberate — keep stage color on the V2
   actor's property keyMoment, or flip the flag?
3. Migration policy for legacy state files with serialized animation keyMoments
   (like downloads/typeroof-20260811-150038.Videoproof.json): regenerate and lift
   user fields, or accept-and-keep?
4. keyMoment-editing UIs don't show inherited values (local-only
   getPropertyValuesMapForKeyMoment) — acceptable when properties move to root?
5. Should regeneration on load be unconditional in videoproof (drop the
   looksLikeNew heuristic) given animation keyMoments are always derived there?
